### Fact-Check Flags (QNX 8.0 Specifics)

1. **Static Linking in QNX 8.0:**
   * Standard QNX SDP 8.0 heavily discourages static linking against `libc`. Standard SDP installations often lack static archive variants (`libc.a`). 
   * Additionally, binaries inside an Image File System (IFS) are loaded into memory directly by QNX’s process manager (`procnto`). Dynamic binaries only require including `libc.so` and `ldqnx.so.2` in the `mkifs` buildfile. Frame static linking as a choice for a minimal demo binary, not as standard QNX architectural best practice.
2. **Default Clock Resolution:**
   * The default QNX kernel clock tick (`ClockPeriod`) is **1 ms (1,000 µs)**. 
   * Without an explicit call to `ClockPeriod()` to request higher timer resolution, `nanosleep(50ms)` on real QNX hardware is limited by this 1 ms tick.

### (a) README Claims Audit

1. **"nothing spoofed"**
   > *Claim:* "a test only counts when the target's own `FDTEST DONE` tallies match what the harness parsed — nothing lost, nothing spoofed"
   * **What's wrong:** Tally verification prevents lost/dropped console lines, but **not spoofing**. Because raw serial text is unauthenticated, a corrupt, rogue, or buggy process printing fake `FDTEST DONE` strings can trick the parser.
   * **Fix:** Change to: *"guarantees complete line capture via end-of-run tally cross-checks."*

2. **"three orders of magnitude tighter"**
   > *Claim:* "Timer drift budgets are set for QEMU/TCG emulation; on real QNX hardware the same checks are typically three orders of magnitude tighter."
   * **What's wrong:** 3 orders of magnitude tighter than 27.8 ms is **~28 microseconds**. On real QNX hardware, standard `nanosleep()` defaults to the 1 ms kernel tick (~28x tighter, not 1000x). Claiming 3 orders of magnitude without mentioning `ClockPeriod()` adjustment will be flagged by QNX kernel engineers.
   * **Fix:** Change to: *"on real QNX hardware with sub-millisecond tick periods, timer accuracy is orders of magnitude tighter."*

3. **Watchdog on Bare-Metal UART vs. QEMU**
   > *Claim 5:* "The serial console is the only channel: deliberately. It works on any QNX target with a UART..." 
   > *Claim 2:* "...if the whole target hangs, the host watchdog restarts the VM"
   * **What's wrong:** The harness restarts QEMU by killing and re-spawning the host QEMU process. Over a pure UART connection to physical hardware, passive serial line monitoring cannot execute a hard board reboot without host-side power-cycle / PDU / relay integration.
   * **Fix:** Clarify that host-driven auto-reboot requires a hypervisor/QEMU control layer or external PDU interface on physical hardware.

### (b) Design Gaps

1. **Multi-Attempt Log Bleed (State Pollution):**
   * If Attempt 1 hangs mid-execution and the watchdog reboots the VM into Attempt 2, the host harness must ensure that partial test lines parsed from Attempt 1 are cleared. Otherwise, duplicate record checks (`problems[]`) will trigger false vetoes across attempts.
2. **Post-`DONE` Hangs:**
   * If the target prints `FDTEST DONE` but hangs during `fdsup` exit or kernel shutdown, the 1.5 s grace window protects the host, but ensure the harness explicitly treats a graceful shutdown timeout post-`DONE` as a harness warning rather than hanging indefinitely.
3. **QNX-Specific Depth (Judging Criteria & Prize):**
   * Standard POSIX IPC/timers run anywhere. To score high on *"Best use of QNX-specific Technologies"*, the test suite should explicitly touch QNX-native APIs (e.g., system page inspection via `syspage_entry_*`, native channel creation `ChannelCreate()`, or message passing with pulse codes `MsgDeliverEvent()`).

---

### (c) Top 3 Recommended Fixes (Impact / Effort)

1. **Tone Down & Correct README Claims (Effort: Very Low | Impact: High)**
   * Correct the three audited claims in the README (remove "nothing spoofed", fix the timer drift wording to reflect 1 ms default ticks, and clarify VM vs. physical hardware watchdog limitations). Judges penalize factual inaccuracies quickly.

2. **Clear Test State on Watchdog Retry (Effort: Low | Impact: High)**
   * In the host harness Python script, ensure that when `attempts[]` appends a watchdog reset event, the target parser state (parsed tests, tallies) resets cleanly for the next attempt so previous partial runs don't pollute `problems[]`.

3. **Add Native QNX Syspage & Architecture Metadata Capture (Effort: Low | Impact: High for QNX Prize)**
   * In `fdsup` or the main native test entry point, read from the QNX System Page (`#include <sys/syspage.h>`) or log system properties (`uname -a`, CPU count from syspage). 
   * Printing this info during target startup and storing it in `report.json` proves deep integration with QNX kernel primitives at near-zero implementation effort.
